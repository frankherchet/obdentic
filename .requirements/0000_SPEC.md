# OBDentic — Initial Product & Architecture Specification

## Problem Statement

Vehicle diagnostics are traditionally split between two unsatisfactory extremes.

Generic OBD-II applications provide easy access to basic standardized values, but expose only a small subset of the information available from modern vehicle control units.

Manufacturer-specific tools such as VCDS expose substantially more information, but much of their value comes from proprietary knowledge about control units, diagnostic identifiers, scaling, interpretation and workflows. Their internal communication is largely opaque to the user.

For AI-assisted diagnostics there is an additional problem: an AI agent needs a safe, structured and machine-readable interface to vehicle telemetry, while the vehicle owner needs to remain able to observe exactly what the agent requests, what is sent to the vehicle and what is returned.

The initial motivation is diagnosis of a 2014 VW Touran 2.0 TDI EA189 with DSG, particularly the intake, EGR and DPF systems. The architecture must, however, not be tied to this vehicle.

The user has existing Bluetooth OBD hardware, including a Carly CUA-V200 adapter and another BLE OBD adapter. OBDentic should reuse suitable existing hardware instead of requiring a proprietary diagnostic interface.

The system must therefore provide:

- transparent communication between an AI agent and the vehicle;
- deterministic decoding of raw diagnostic data;
- vehicle-specific knowledge without embedding it into the UI or AI;
- time-series telemetry and logging;
- a rich terminal interface;
- a safe read-only architecture;
- an MCP interface usable by Codex;
- reproducible offline analysis of recorded vehicle sessions;
- extensibility to additional adapters, vehicles and control units.

## Solution

Build **OBDentic**, a local vehicle diagnostics and telemetry system centered around a terminal user interface and a read-only diagnostic core.

OBDentic connects to an OBD adapter, initially over Bluetooth Low Energy, and owns the physical diagnostic connection to the vehicle.

Codex connects to OBDentic through MCP rather than communicating with the adapter directly.

OBDentic translates semantic requests such as:

`read DPF differential pressure`

into the appropriate vehicle-specific diagnostic request.

It then:

1. sends the request through the configured adapter;
2. records the transmitted bytes;
3. records the vehicle response;
4. deterministically decodes the raw response;
5. stores the resulting telemetry sample;
6. presents the complete transaction in the TUI;
7. returns structured data to Codex.

The TUI should resemble tools such as btop, lazygit and Codex CLI rather than a conventional desktop automotive application.

Codex is responsible for deciding **which information is diagnostically relevant** and may dynamically change the displayed telemetry layout.

OBDentic is responsible for determining **what the bytes mean**.

This yields the central architectural principle:

> The vehicle profile translates bytes into facts; Codex translates facts into diagnosis and presentation.

All diagnostic communication is visible to the vehicle owner.

The initial implementation is strictly read-only. Potentially mutating diagnostic services are rejected by the diagnostic core regardless of what a client requests.

## User Stories

1. As a vehicle owner, I want OBDentic to connect to my vehicle through a Bluetooth OBD adapter, so that I can access vehicle diagnostics without proprietary desktop hardware.

2. As a vehicle owner, I want OBDentic to automatically reconnect to a previously configured adapter, so that starting a diagnostic session is quick.

3. As a vehicle owner, I want to see whether the adapter, vehicle and target ECU are connected, so that connection failures are obvious.

4. As a vehicle owner, I want to see exactly which command Codex requests, so that AI diagnostics are transparent.

5. As a vehicle owner, I want to see the diagnostic request actually transmitted to the vehicle, so that semantic AI requests do not hide lower-level behavior.

## Implementation Decisions

- The project name is **OBDentic**.

- OBDentic is a local-first application.

- The initial target environment is macOS with a Bluetooth Low Energy OBD adapter.

- The initial vehicle is a VW Touran 1T, model year 2014, 2.0 TDI EA189 with 6-speed DSG.

- The initial diagnostic focus is the engine ECU and particularly intake, EGR and DPF telemetry.

- Carly CUA-V200 is an initial adapter target because suitable hardware is already available.

- A second existing BLE OBD adapter may be implemented as an additional transport and useful comparison/reference implementation.

- Adapter implementations and vehicle knowledge are separate concerns.

- The system consists conceptually of:
  - adapter transports;
  - diagnostic protocol/core;
  - vehicle profiles and decoders;
  - telemetry scheduler and time-series storage;
  - session logger/replayer;
  - TUI;
  - MCP interface.

- A single process or daemon owns the physical adapter connection. Multiple components must not independently compete for the BLE connection.

- TUI and MCP operate through the same diagnostic core.

- The implementation may initially be a single executable with multiple operating modes rather than multiple separately distributed programs.

- The diagnostic core exposes semantic signals rather than requiring upper layers to understand raw diagnostic requests.

- Raw diagnostic access is an implementation/debugging capability and must not be the primary Codex API.

- Vehicle profiles contain deterministic decoding information.

- Signal decoding includes, where applicable:
  - ECU identity/address;
  - protocol/service;
  - PID/DID or equivalent identifier;
  - response location;
  - integer representation;
  - signedness;
  - byte order;
  - scaling;
  - offset;
  - physical unit;
  - plausible range;
  - provenance;
  - description.

- Arbitrary executable expressions should not be accepted from untrusted profiles for signal decoding. Complex conversions should use known decoder implementations or another constrained representation.

- Signal definitions are versionable.

- Decoder provenance/confidence is explicit.

- At minimum the system distinguishes verified information from experimental or inferred information.

- Raw bytes are retained alongside decoded telemetry.

- Logging preserves enough metadata to re-decode historical recordings with a newer decoder.

- Telemetry acquisition is subscription based.

- The telemetry engine owns repeated polling.

- Codex requests which signals should be observed and at what desired rate; Codex does not make an MCP round trip for every individual telemetry sample.

- The telemetry scheduler accounts for transport and ECU limitations and may negotiate or reduce requested rates.

- The UI consumes the same telemetry stream as MCP and logging.

- TUI layouts are declarative data, not hard-coded screens.

- Layouts reference semantic signal names rather than diagnostic identifiers.

- Layouts can contain current-value panels, gauges, history/sparkline views and time-series comparisons.

- Layout definitions can be generated or modified by Codex and persisted for reuse.

- A saved layout does not contain vehicle-specific decoding logic.

- Missing signals in a layout are reported rather than fabricated.

- MCP tools should be semantic and relatively high-level.

- Initial MCP capabilities should cover:
  - vehicle and ECU information;
  - available signal discovery;
  - current snapshots;
  - diagnostic trouble-code reading;
  - semantic signal reading;
  - telemetry subscriptions;
  - DPF-related status;
  - EGR/intake-related status;
  - recording controls;
  - recording/replay access;
  - TUI layout operations.

- The diagnostic core is read-only in the initial product.

- Read-only safety is enforced below MCP.

- Mutating diagnostic services are blocked regardless of client behavior.

- The initial implementation must not expose coding, adaptations, actuator tests, basic settings, DTC clearing, security access or arbitrary write-oriented diagnostic services.

- Blocked requests are logged and visible.

- Offline replay is a first-class architecture requirement rather than a later convenience feature.

- Replay should enter the system at the highest practical diagnostic/transport seam so that decoder, telemetry, MCP and UI behavior can be exercised without a vehicle.

- The Carly transport implementation is expected to require investigation of its proprietary BLE protocol.

- Carly protocol investigation should begin with BLE service and characteristic enumeration followed by small controlled captures.

- Android with Carly, ADB and Bluetooth HCI snoop logging can be used to observe legitimate communication between the existing Carly application and owned adapter.

- Protocol investigation should use minimal controlled experiments, such as connecting and observing one known value, rather than collecting large undifferentiated captures.

- Carly-specific framing belongs only in the Carly adapter driver.

- OBDentic must not depend on Carly application services, cloud infrastructure or subscription services for normal operation.

- Standard OBD-II support should be implemented early because known signals such as RPM provide an effective transport validation target.

- The first vertical slice is:
  1. discover/connect adapter;
  2. communicate with vehicle;
  3. request a known value such as RPM;
  4. receive its raw response;
  5. deterministically decode the response;
  6. show the complete request/response/decode path in the TUI;
  7. make that value available through the internal semantic API.

- MCP should be added after the local vertical slice proves the transport and diagnostic core.

- EA189 manufacturer-specific values should be added incrementally after basic communication is proven.

- OBDentic is not conceptually tied to Volkswagen, EA189 or Carly. These are the first supported profile and adapter.

- A later version may embed the Codex experience directly into the OBDentic TUI. The first version should instead expose OBDentic to an independently running Codex instance through MCP.

## Testing Decisions

### Primary test seam

The preferred high-level test seam is the **Diagnostic Core through an interchangeable transport/replay boundary**.

Tests provide recorded or synthetic transport responses to the same core used with a physical adapter and observe externally meaningful behavior above it.

This allows a large portion of the system to be tested through one principal seam:

- diagnostic request construction;
- safety policy;
- raw response handling;
- vehicle profile decoding;
- telemetry samples;
- semantic API responses;
- session recording;
- MCP behavior;
- TUI model/state.

Tests should avoid asserting private implementation details such as individual helper calls or internal data structures.

A good test should state behavior such as:

> Given a known EA189 response for a supported DPF signal, requesting `dpf.diff_pressure` returns the expected value and unit, stores the raw transaction, and exposes the same decoded value to telemetry consumers.

rather than:

> Decoder helper X invokes parser helper Y with argument Z.

### Transport integration seam

Physical adapter drivers require separate integration tests because BLE behavior cannot be faithfully proven by unit tests alone.

These tests should verify externally observable transport behavior:

- adapter discovery;
- connection;
- GATT service/characteristic selection;
- message send;
- notification receive;
- disconnect/reconnect;
- timeout behavior.

Captured traffic should be usable in automated regression tests wherever practical.

### Replay tests

Known recorded sessions should serve as regression fixtures.

Replaying the same session against the same profile version should yield deterministic decoded telemetry.

Updated decoder versions may intentionally yield different decoded values, but raw traffic must remain unchanged and the profile/decoder version must make the difference explainable.

### Safety tests

Safety tests must operate at the diagnostic-core boundary and prove that prohibited mutating services never reach the transport.

The observable assertion is that:

- the client receives a denial;
- the denial is logged;
- no outgoing transport request for the prohibited operation occurs.

This is a critical invariant.

### Vehicle profile tests

Profiles should be tested using known raw request/response fixtures.

Tests verify physical value, unit, range handling and provenance exposed by the semantic interface.

### TUI tests

TUI testing should focus on state and behavior rather than terminal rendering internals.

Examples:

- adding a telemetry subscription causes the signal to appear;
- switching a signal to time-series mode retains history;
- applying a stored layout requests its declared semantic signals;
- unavailable signals are visibly represented as unavailable;
- Codex activity and raw diagnostic activity remain distinguishable.

Snapshot tests may be used selectively for stable high-level screens, but should not become the primary verification technique.

### MCP tests

MCP tests should exercise the public semantic tool surface against the same diagnostic-core/replay seam.

A client should receive the same semantic facts whether the underlying transport is live or replayed where the operation permits replay.

### Initial acceptance test

The first meaningful end-to-end acceptance test is:

- start OBDentic;
- connect to a supported adapter;
- connect to the vehicle;
- read engine RPM;
- show semantic request;
- show raw transmitted diagnostic request;
- show raw vehicle response;
- show decoded RPM;
- record the interaction;
- replay the recording and reproduce the decoded result.

## Out of Scope

The initial specification does not include:

- vehicle coding;
- adaptation changes;
- actuator tests;
- basic settings;
- DTC clearing;
- ECU flashing;
- immobilizer functions;
- SecurityAccess workflows;
- arbitrary UDS write access;
- arbitrary CAN frame injection;
- replacement of VCDS as a complete Volkswagen workshop diagnostic suite;
- automatic vehicle repair decisions;
- autonomous control of vehicle functions;
- write access based merely on user confirmation;
- reverse engineering or bypassing Carly subscription/account controls;
- dependency on Carly cloud services;
- a graphical desktop UI;
- mobile applications;
- cloud telemetry storage;
- multi-user or fleet management;
- support for every ECU in the Touran in the first milestone;
- broad multi-manufacturer vehicle coverage in the first milestone;
- direct Codex embedding in the initial TUI;
- real-time safety-critical vehicle control.

## Further Notes

The motivating diagnostic use case is investigation of recurring intake/EGR contamination and general DPF health on an EA189 diesel with approximately 185,000 km.

The project originated from the observation that traditional diagnostic software combines two separate assets:

1. communication hardware capable of talking to vehicle control units;
2. manufacturer-specific knowledge required to interpret those communications.

OBDentic intentionally separates these.

A suitable commodity or existing adapter provides transport.

Vehicle profiles provide deterministic automotive knowledge.

Codex provides adaptive reasoning, diagnostic workflow selection and presentation.

This separation is intended to allow increasingly rich vehicle-specific diagnostics without coupling the project to a proprietary diagnostic interface.

Transparency is a defining product requirement rather than merely a debug feature.

At any point the user should be able to answer:

- What did Codex ask for?
- What did OBDentic translate that into?
- What bytes were sent to the vehicle?
- What did the vehicle return?
- How did OBDentic decode those bytes?
- What information was returned to Codex?

The long-term product concept is a general **Codex Vehicle Interface** with OBDentic as the standalone transparent diagnostics and telemetry layer.

EA189/Touran support is the proving ground, not the architectural boundary.
