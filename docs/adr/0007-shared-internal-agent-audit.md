# 0007. Shared internal storage for the agent audit
Date: 2026-11-19
Status: proposed

## Context

Spike #363, amended by its owner, investigates #355 and accepted REQ-045.10–.12 and .23–.33. The approved amendment replaces the original app-private/no-backup and Keystore comparison: the user explicitly chooses shared **internal** device storage for unencrypted JSONL, visible to a file manager. OBDentic does not automatically upload or back up the audit or select a remote provider. Other apps or the user may copy or back it up; OBDentic's export warning and redaction preview cannot govern such copies. The model cannot choose the destination. Fail closed even for offline tools; do not substitute a directory. This ADR does not change approved requirements.

The spike is one focused design/refinement session with synthetic data only. This pass authorizes no prototype, measurement, device, model, account, vehicle, or private payload. Its question is whether a supported Android configuration can establish a local selected destination, durable-before-dispatch and the approved latency, retention and budget behavior—not whether an arbitrary SAF provider claims to support writing.

## Options considered

1. **Generic SAF tree, trusting the picker or local flag:** insufficient evidence for internal-only storage or durability across all providers; not a basis for dispatch.
2. **Candidate vetted platform local provider and primary internal volume, selected through SAF:** investigate against a specifically identified Android build/provider and filesystem, with persistent permission, explicit local/internal validation, a proven synchronization boundary, and strict error handling. Reject unknown provider, root, capabilities or lost permission. This is a hypothesis, not an approved or established implementation; SAF alone may not expose the directory synchronization needed for new files.
3. **Unsupported destination or unprovable durability:** refuse work and report the error. No private-storage fallback, alternate folder or asynchronous audit dispatch. This protects the contract but does not by itself establish the normal flow.

## Measurements

No experiments, commands, device observations, latency samples or interruption measurements were performed. The following are source/code observations, not benchmark results:

- [Android SAF](https://developer.android.com/training/data-storage/shared/documents-files) describes user selection of a tree and access to its descendants; providers can include cloud and external volumes. Android 11+ restricts selection of the internal volume root, Download itself, and other paths. A selectable child directory must be chosen. A URI is not a filesystem path or proof of an internal volume.
- [`Intent.EXTRA_LOCAL_ONLY`](https://developer.android.com/reference/android/content/Intent#EXTRA_LOCAL_ONLY) requests data on the local device; it does not establish the approved *internal* volume, absence of later external copies, or a durable append. [`Root.FLAG_LOCAL_ONLY`](https://developer.android.com/reference/android/provider/DocumentsContract.Root#FLAG_LOCAL_ONLY) is provider-reported metadata, not independent evidence of internal-device provenance. Do not rely solely on either. [AOSP ExternalStorageProvider at a pinned revision](https://android.googlesource.com/platform/frameworks/base/+/09a5fd6012af3528280ebb71507b27d5ff4ee96a/packages/ExternalStorageProvider/src/com/android/externalstorage/ExternalStorageProvider.java) maps document IDs to volumes and marks local roots including removable volumes; its primary-emulated root is an implementation-specific candidate, not a portable guarantee that every OEM build has those semantics.
- SAF grants can be persisted with `takePersistableUriPermission` when offered; [Android documentation](https://developer.android.com/training/data-storage/shared/documents-files#persist-permissions) warns that moved/deleted documents can invalidate access. Persist only granted read/write flags, retain the tree URI, check it and handle actual operation failures or revocation each time; a persisted grant is not a durability certificate.
- [`ContentResolver.openFileDescriptor`](https://developer.android.com/reference/android/content/ContentResolver#openFileDescriptor(android.net.Uri,%20java.lang.String)) permits a pipe/socket for exclusive read or write modes; `rw` implies a seekable on-disk file, but does not promise internal storage, crash-durable provider metadata, or an independently verifiable directory sync. Mode semantics are provider-dependent. A stream flush, close, successful write, read-back or process restart is not proof of durable storage.
- For an actual local filesystem descriptor, [Linux `fsync(2)`](https://man7.org/linux/man-pages/man2/fsync.2.html) says successful `fsync` waits for the device-reported data and file metadata transfer, but does **not** necessarily persist a newly created/renamed file's parent directory entry: that needs a directory descriptor and separate `fsync`. Device/controller honesty and filesystem/provider behavior remain assumptions. The generic SAF contract cited above does not expose a universal parent-directory fsync guarantee. File-sync acknowledgement, survival of the file contents, and survival of its name are distinct claims; an existing proven-durable file and a newly created session file have different prerequisites.
- Repository `android/app/build.gradle` declares minSdk 26 and targetSdk 36. `MainActivity.java:683–686,878–886` already uses tree selection and persisted grants for **recording export**, with an initial URI hint. It neither validates audit-local internal storage nor establishes audit append durability; an initial URI is not a restriction. It is not evidence of an agent-audit implementation.

## Uncertainty

**Paper dry run and approved amendment:** The original wording could count the lack of a generic SAF guarantee as refutation even if a vetted configuration would satisfy confirmation. The owner approved assessing both criteria against the same named supported Android/provider configuration and its documented boundary. This resolves the scope ambiguity without changing REQ-045, relaxing fail-closed rules, or accepting feasibility. Define the interruption model and durability acknowledgement oracle before measurement; a sync return is not independent evidence of post-power-loss survival.

The tentative reference for a later experiment is the existing documented Mi 9T / Android 16 (API 36) from ADR 0005, with targetSdk 36 and a user-selected child of primary shared internal storage served by the system external-storage documents provider. This is a **candidate**, not a supported configuration or a new device observation. Record exact build fingerprint, provider package/version/signature and authority, volume/root mapping, filesystem/mount/FUSE path, picker and granted flags before any test. Verify against the specific build's source or authoritative implementation; reject remote, unknown, removable and ambiguous roots. An authority name or `primary:` string alone is not an OEM-independent trust proof. No threat model promises protection from privileged/rooted actors, external file-manager copying, backups or physical compromise.

## Decision

**No GO or NO-GO on feasibility.** Investigate the vetted local-provider option under the approved configuration-specific criterion; this ADR itself remains proposed. Until a named configuration demonstrates the complete durable append boundary and the approved criteria, unconfirmed durability is a stop, not permission to dispatch. No benchmark exception, alternate directory or product criteria change is authorized.

## Consequences

- Next discriminating experiment, separately authorized and synthetic-only: first verify the candidate build/provider and whether a newly created session file's parent directory can be durably synchronized via a legitimate app-accessible interface. Compare a newly created file with an already established file; if parent sync is unavailable and no provider-backed equivalent is documented and demonstrable, record the gap rather than calling a successful file sync durable. Check selection of primary internal child vs cloud/removable/unknown providers, persisted grant across restart, revoke/move/delete and failing opens; each invalid case must produce exactly zero simulated dispatches, without fallback.
- Inject short writes, full storage, permission loss, file-sync and directory-sync failure, process termination at create/write/sync/ack/dispatch boundaries, and separately controlled abrupt system/storage interruption on a disposable reference device or a fault-injection setup with a defined persistence oracle. Capture independent pre-interruption sequence/ack markers and post-recovery bytes/name and inspect torn lines, missing end markers and uncertain dispatch. Test failures before acknowledgement separately from loss after acknowledgement; graceful reboot and app force-stop are not power-loss proof. If an abrupt interruption or trustworthy oracle is unavailable, its durability verdict remains inconclusive.
- Synthetic boundary matrix: completed session at just before/exactly/after 30 days; active and missing verified end never auto-expire; warning before further work at 80% of 256 MiB including incomplete and active bytes; exact and one-byte-over 256 MiB total, 32 MiB session, and 2 MiB encoded event; 10,000th and attempted 10,001st event. Check no truncation, unauthorized eviction, or unaudited dispatch. Include full-storage and interrupted-end-marker inspection.
- Predeclare the latency method before sampling: monotonic clock from each append request through the **actual proven** durability confirmation, including any file/directory synchronization required by that case; use synthetic complete outbound JSONL records of sizes through 64 KiB. Record device/build, filesystem, free space, thermal/power state, workload, sample count, every raw duration and failure; report nearest-rank p95 separately for cold (fresh process and newly established file where applicable) and warm (repeated appends), without dropping failed or slow writes. A proposed minimum is 100 successful samples per stratum, with failures separately counted as failures rather than silently discarded; this sample size does not prove tail behavior or authorize changing the approved 25 ms target. Define cold-cache control and repetitions before running; if cold storage state cannot be established label it process-cold, not storage-cold. Exceeding 25 ms in an applicable measured stratum refutes the target; missing a proven acknowledgement, representative coverage or sufficient samples is inconclusive, not PASS.
